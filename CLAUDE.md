## Project Overview

Discord Message Summarizer - Phase 1: A Python 3.11+ CLI application that processes Discord channel conversations from JSONL fixtures and generates structured summaries, deltas, and digests using GLM4.7 (Z.ai) LLM.

**Key Technologies:**
- Python 3.11+, Typer (CLI), Pydantic (models), Rich (terminal UI)
- SQLite for persistent storage
- Z.ai GLM4.7 API with mock mode for testing
- Event-driven architecture via EventBus
- pytest for testing

pip install -e .

### CLI Usage
```bash
# Ingest fixtures into database
python -m app.cli ingest --db data/app.db --fixture fixtures/sample_3days.jsonl --reset

# Run for specific date
python -m app.cli run --db data/app.db --date 2026-01-16

# Run for date range (chained deltas)
python -m app.cli run --db data/app.db --start 2026-01-15 --end 2026-01-17

# Fast dev loop (last hour)
python -m app.cli run --db data/app.db --last-hours 1

# Preview single channel
python -m app.cli preview --db data/app.db --date 2026-01-17 --channel-name alice

# Run with mock LLM (no API calls)
python -m app.cli run --db data/app.db --date 2026-01-16 --mock
```

## Architecture Overview

### Event-Driven Architecture

The system uses an EventBus (`src/core/events.py`) for loose coupling:

**Event Types:**
- `MESSAGE_INGESTED`: Messages loaded from fixtures
- `STATE_GENERATED`: Daily state created by LLM
- `DELTA_COMPUTED`: Changes calculated between days
- `DIGEST_CREATED`: Global digest generated
- `ERROR`: Error occurred

**EventBus API:**
- `subscribe(event_type, callback)`: Subscribe to events
- `publish(event)`: Publish event to all subscribers
- `get_history(event_type)`: Get event history, optionally filtered
- `enable()/disable()`: Control event publishing

**Critical Pattern:** Subscriber errors are isolated - one failing subscriber doesn't break the bus. Events are published with threading.Lock for thread safety.

### Layered Architecture

```
src/
├── app/cli.py              # CLI entry point (Typer commands)
├── core/                   # Business logic
│   ├── models.py           # Pydantic data models
│   ├── events.py           # EventBus implementation
│   ├── summarizer.py       # LLM-based summarization
│   ├── delta.py            # Delta computation (set differences)
│   ├── digest.py           # Global digest aggregation
│   ├── renderer.py         # Markdown rendering
│   └── timewindow.py       # Time window management (Asia/Seoul)
├── infra/                  # Infrastructure layer
│   ├── db.py               # SQLite operations (pure sqlite3, no ORM)
│   ├── glm_client.py       # GLM4.7 API client with retry logic

└── security/               # Security module

    ├── validators.py
    ├── rate_limiter.py
    └── audit_logger.py
```

### Data Flow

1. Messages ingested from JSONL fixtures into SQLite (`messages` table)
2. DailyChannelState generated by GLM4.7 for each channel/date (stored in `daily_channel_state`)
3. Delta computed between consecutive days via set differences (`daily_channel_delta`)
4. GlobalDigest aggregates across all channels (`global_digest`)
5. Results rendered as Markdown using `rich` library

### Key Data Models (Pydantic)

All models in `src/core/models.py`:

- **MessageEvent**: Input record (message_id, channel, author, content, attachments, links)
- **DailyChannelState**: Structured JSON state (topics, progress, artifacts, help_requests)
- **DailyChannelDelta**: Changes between consecutive days (set differences, not message diff)
- **GlobalDigest**: Aggregated highlights across channels

**Important:** DailyChannelState must remain stable - deltas depend on JSON-to-JSON comparison.

### Database Schema (SQLite)

Tables in `src/infra/db.py`:
- `messages`: Message data with indexes on (channel_id, created_at) and (channel_name, created_at)
- `daily_channel_state`: Generated states and summaries, PRIMARY KEY (date, channel_id)
- `daily_channel_delta`: Computed deltas, PRIMARY KEY (date, channel_id)
- `global_digest`: Global digests, PRIMARY KEY (date)

**Pattern:** Pure sqlite3 with parameterized queries (no ORM). Use `tempfile.NamedTemporaryFile` for database tests to ensure isolation.

## Important Implementation Patterns

### Dependency Injection

EventBus is injected via constructors, not globals:
```python
# Components receive EventBus in constructor
db = Database(event_bus=event_bus)
glm_client = GLMClient(event_bus=event_bus)
```

This enables testing with mock EventBus instances for event tracking.

### Rich Terminal Output

The CLI uses `rich` library extensively:
- **Progress bars**: For long-running operations (ingest, run)
- **Tables**: For structured data (ingest summary, messages, test results)
- **Panels**: For highlighted information (summaries, deltas, digests)
- **Colors**: green (success), red (error), yellow (warning), cyan (info)

### Time Window Handling

Default timezone: `Asia/Seoul`. Three modes in `src/core/timewindow.py`:
- **Date mode**: `--date YYYY-MM-DD` → full day in KST
- **Range mode**: `--start/--end` → run date mode for each day sequentially
- **Pseudo-day mode**: `--last-hours N` → rolling window from now-N hours to now

### Mock Mode for Testing

The `--mock` flag enables fast, deterministic testing without API calls:
```bash
python -m app.cli run --mock --date 2026-01-17
```

Mock mode returns predictable JSON responses. All tests use mock mode by default; only e2e tests use real GLM API when `GLM_API_KEY` is present.

### Error Handling

- Subscriber errors are isolated in EventBus (wrapped in try/except)
- Database uses parameterized queries to prevent SQL injection
- Returns None for missing data instead of raising exceptions
- Use context managers for database connections

### Pydantic Patterns

Always use `Field(default_factory=list)` for mutable defaults:
```python
class DailyChannelState(BaseModel):
    topics: list[str] = Field(default_factory=list)  # Correct
    # NOT: topics: list[str] = []  # Wrong - shared mutable default
```

## Self-Test Command

The `selftest` command (`python -m app.cli selftest`):
1. Creates temporary database (isolated from real data)
2. Ingests fixtures
3. Runs full pipeline across 3-day range
4. Validates states, deltas, and digests exist with correct content
5. Displays results in rich table with PASS/FAIL indicators
6. Exits with non-zero code on failures

## Testing Strategy

- **Unit tests**: Individual components (db, delta, events, timewindow, summarizer)
- **Integration tests**: Component interactions with mock LLM
- **E2E tests**: Full pipeline with real GLM API (only when API key present)
- **Event tracking**: Tests subscribe to events and assert they were published with correct data

Target: 53+ tests (baseline). The codebase achieved 89 tests in previous iterations.
